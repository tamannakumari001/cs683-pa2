\section{Task 1: Stride Pattern Prefetching}

% ---------------------------------------------------------------- Task 1A
\subsection{Task 1A: Understanding the IP-stride prefetcher}
\label{sec:task1a}

\subsubsection{How the prefetcher works}

The IP-stride prefetcher (\texttt{prefetcher/ip\_stride.l1d\_pref}) sits at the L1 data
cache. Its idea is that a single load or store instruction, identified by its instruction
pointer (IP), tends to walk through memory with a constant stride (for example, a loop
over an array). It remembers the last address each IP touched, computes the stride between
consecutive accesses of that IP, and once the same stride is seen twice in a row it
prefetches the next few addresses along that stride. The code is walked through below,
section by section; the line numbers in the listings are the line numbers in the source file.

\paragraph{1.\ Parameters and the tracker entry (lines 4--30).}
\lstinputlisting[language=C++, firstline=4, lastline=30, firstnumber=4]{../prefetcher/ip_stride.l1d_pref}
\begin{itemize}
    \item \texttt{IP\_TRACKER\_COUNT = 24}: the prefetching table has only 24 entries.
    \item \texttt{PREFETCH\_DEGREE = 3}: when the prefetcher fires it issues 3 prefetches. The
          degree is fixed and never changes.
    \item \texttt{MASK\_IP = 0xFF}: only the low 8 bits of the IP are used to identify an
          instruction. Different instructions whose IPs share the low 8 bits therefore
          share one tracker (aliasing).
    \item Each \texttt{IP\_TRACKER} entry stores: the (masked) IP it belongs to; the cache-line
          address of the last access by that IP (\texttt{last\_cl\_addr}); the stride observed
          between its last two accesses (\texttt{last\_stride}, signed, in cache lines); and an
          LRU rank used to choose which entry to replace when the table is full.
    \item The table \texttt{trackers[]} is a single global array, so it is shared by everything that
          uses this prefetcher (fine for the single-core configuration used here).
\end{itemize}

\paragraph{2.\ Initialisation (lines 33--39).}
\lstinputlisting[language=C++, firstline=33, lastline=39, firstnumber=33]{../prefetcher/ip_stride.l1d_pref}
This function is called once when the simulation starts. It prints a banner and gives the 24
entries the distinct LRU ranks $0,1,\dots,23$. Rank 0 means most recently used and rank 23
(\texttt{IP\_TRACKER\_COUNT-1}) means least recently used, so at any time the ranks form a
permutation of $0\ldots23$ and exactly one entry is the replacement victim. All entries start
with \texttt{ip = 0}, \texttt{last\_cl\_addr = 0} and \texttt{last\_stride = 0}.

\paragraph{3.\ Entry point: cache-line address and IP (lines 41--46).}
\lstinputlisting[language=C++, firstline=41, lastline=46, firstnumber=41]{../prefetcher/ip_stride.l1d_pref}
\texttt{l1d\_prefetcher\_operate} is called by the L1D for each access it handles. The
prefetcher works on cache lines, not bytes: shifting the byte address right by
\texttt{LOG2\_BLOCK\_SIZE} drops the offset inside the 64-byte line, giving \texttt{cl\_addr}.
The IP is reduced to its low 8 bits. The arguments \texttt{cache\_hit} and \texttt{type} are
not used in this file, so the prefetcher trains on every access it is called for, whether it
hit or missed in the L1D.

\paragraph{4.\ Looking up the tracker (lines 48--52).}
\lstinputlisting[language=C++, firstline=48, lastline=52, firstnumber=48]{../prefetcher/ip_stride.l1d_pref}
The table is fully associative: a linear search compares the masked IP against every entry.
If an entry matches, the loop \texttt{break}s with \texttt{index} pointing at it. If none
matches, the loop runs to the end and \texttt{index} equals \texttt{IP\_TRACKER\_COUNT}.

\paragraph{5.\ A new IP: allocating a tracker (lines 54--74).}
\lstinputlisting[language=C++, firstline=54, lastline=74, firstnumber=54]{../prefetcher/ip_stride.l1d_pref}
\begin{itemize}
    \item \textbf{Choosing the victim (57--60).} The entry whose LRU rank is 23 (the least
          recently used) is selected for replacement.
    \item \textbf{Initialising it (62--64).} The entry is overwritten with the new IP and the
          current line address. \texttt{last\_stride} is set to 0 because no stride is known yet.
    \item \textbf{LRU update (67--71).} Every entry that was more recently used than the victim
          (rank smaller than the victim's) moves one step towards ``old'' (rank $+1$), and the new
          entry becomes rank 0. Since the victim had rank 23, all other entries are incremented
          and the ranks remain a permutation.
    \item \textbf{No prefetch (73).} With only one address seen, there is no stride to
          compute, so the function returns without prefetching.
\end{itemize}

\paragraph{6.\ Sanity check and stride calculation (lines 76--90).}
\lstinputlisting[language=C++, firstline=76, lastline=90, firstnumber=76]{../prefetcher/ip_stride.l1d_pref}
When execution reaches here, a tracker for this IP exists. The \texttt{assert} guards against
an impossible state. The stride is the difference between the current and the previous cache-line
address of this IP, in units of cache lines. Because the addresses are unsigned, the code
subtracts the smaller from the larger and negates the result if the access moved backwards, so a
descending access pattern gives a negative stride.

\paragraph{7.\ Ignoring repeated lines (lines 94--96).}
\lstinputlisting[language=C++, firstline=94, lastline=96, firstnumber=94]{../prefetcher/ip_stride.l1d_pref}
A stride of 0 means the same cache line was accessed again (for example several accesses to the
same line). There is nothing to learn or prefetch from that, so the function returns early. Note
that this early return does \emph{not} update \texttt{last\_cl\_addr}, \texttt{last\_stride} or the
LRU ranks.

\paragraph{8.\ The trigger and the prefetch loop (lines 98--117).}
\lstinputlisting[language=C++, firstline=98, lastline=117, firstnumber=98]{../prefetcher/ip_stride.l1d_pref}
\begin{itemize}
    \item \textbf{Trigger (100).} Prefetching only happens if the new stride equals the stored
          \texttt{last\_stride}, i.e.\ the same stride has been seen twice in a row. This is the
          prefetcher's only form of confidence: one repetition. Since a new entry starts with
          \texttt{last\_stride = 0}, an IP needs three accesses before its first prefetch (the first
          allocates the entry, the second records the stride, the third confirms it).
    \item \textbf{Addresses (103--104).} For $i = 0,1,2$ it prefetches the line at
          \texttt{cl\_addr + stride $\cdot (i+1)$}, converted back to a byte address, so with stride $s$
          it prefetches the next three lines along the pattern. 
    \item \textbf{Page boundary (108--109).} The prefetch address must be in the same 4~KB page as
          the demand access (the usual reason is that consecutive
          pages are not necessarily contiguous or even mapped, so a stride run cannot safely be
          followed across a page. Also the prefetcher does not know whether the next page is actually valid/mapped.). On the first violation the loop
          stops, since the later prefetches in the same direction would also be outside the page.
    \item \textbf{Fill level (112--115).} \texttt{prefetch\_line} hands the request to the cache. If
          fewer than half of the L1D MSHR entries are in use the line is brought into the L1D
          (\texttt{FILL\_L1}); otherwise it is only brought into the L2 (\texttt{FILL\_L2}), so that
          prefetches do not use up the miss-handling resources that demand misses need.
\end{itemize}

\paragraph{9.\ Updating the entry (lines 119--128).}
\lstinputlisting[language=C++, firstline=119, lastline=128, firstnumber=119]{../prefetcher/ip_stride.l1d_pref}
Whether or not a prefetch was issued, the entry now remembers the current line address and the
current stride, ready for the next access of this IP. The entry then becomes the most recently
used: every entry that was more recent than it is aged by one and it gets rank 0. Note that only
the \emph{last} stride is kept as history; one irregular access overwrites it.

\paragraph{10.\ Fill hook and final statistics (lines 130--139).}
\lstinputlisting[language=C++, firstline=130, lastline=139, firstnumber=130]{../prefetcher/ip_stride.l1d_pref}
\texttt{l1d\_prefetcher\_cache\_fill} is called whenever a line is filled into the L1D. This
prefetcher does not use it (the body just returns). \texttt{l1d\_prefetcher\_final\_stats} prints the
degree at the end of the simulation. There is no accuracy tracking in this prefetcher; the
accuracy reported in the results comes from ChampSim's own prefetch counters.

\subsubsection{Limitations}
The IP-stride prefetcher only works for accesses with one constant stride per IP. Its main
limitations, which motivate SPP, are:
\begin{itemize}
    \item \textbf{No tolerance to irregularity.} Each entry stores a single stride and a single
          previous address, and a prefetch is issued only when $s_n = s_{n-1}$, where
          $s_n = A_n - A_{n-1}$. One irregular access overwrites \texttt{last\_stride}, so the
          next access cannot match it and the stride has to be re-learned and re-confirmed. A single
          irregular access therefore suppresses prefetching for about two subsequent accesses.
          There is no confidence counter that could absorb such noise.
    \item \textbf{Cannot learn alternating or periodic strides.} Patterns whose stride sequence is
          periodic but not constant, such as $\{+1,+3,+1,+3,\dots\}$, never produce two equal
          consecutive strides, so no prefetch is ever issued even though the pattern is fully
          predictable. Typical sources are structure-of-fields traversals, padded 2D arrays and
          nested loops. Only one delta of history is kept, so such patterns cannot be captured.
    \item \textbf{No support for irregular or indirect accesses.} Pointer chasing and indirect
          accesses such as \texttt{A[B[i]]} have no constant stride, so the prefetcher gives no
          benefit and only trains on noise.
    \item \textbf{Training delay.} An IP needs three accesses before its first prefetch, which
          hurts short loops and short streams.
    \item \textbf{Page boundary.} Prefetching stops at the 4\,KB page boundary and each new page
          has to be trained again, so the lookahead is truncated near the end of every page.
    \item \textbf{Fixed degree and no feedback.} The degree is fixed and is not adapted to
          accuracy or timeliness, so the prefetcher may be too aggressive on irregular code
          (cache pollution, wasted bandwidth) or too shallow on regular code.
    \item \textbf{Per-IP table pressure.} Training state is kept per IP in a small LRU table.
          Programs with many load IPs thrash it, and patterns learned by one IP cannot be shared
          with other IPs that behave identically.
\end{itemize}
SPP addresses these by keeping a history of several recent deltas (a signature) and by predicting
the next delta from that history, so alternating patterns can be captured and a single irregular
access does not destroy the learned state.

\paragraph{Observations.}
\begin{itemize}
    \item \textbf{Performance gain is negligible.} The speedups are $1.005$, $1.000$ and $1.002$,
          so IP-stride changes IPC by at most 0.5\%.
    \item \textbf{Coverage is low}, only $5.3\%$, $0.7\%$ and $2.5\%$ of the baseline L1D load misses
          are removed. Trace2 gains almost nothing, and it is also the trace with the highest baseline
          L1D load MPKI ($13.5$), so there is plenty of room that the prefetcher does not use.
    \item \textbf{Accuracy varies a lot between traces}: $53.0\%$, $38.2\%$ and $16.0\%$. In Trace3
          the useless prefetches ($10\,595$) are almost four times the useful ones ($2\,713$), and the
          late prefetches ($3\,067$) outnumber the useful ones, so many prefetches also arrive after
          the demand access.
    \item \textbf{Most prefetches never leave the L1D.} Of the prefetches that look up the L1D, $80.2\%$,
          $84.4\%$ and $84.1\%$ (Trace1, 2, 3) find the line already present (the \texttt{L1D PREFETCH}
          hit rate), so they fetch nothing. Only $19.9\%$, $14.5\%$ and $16.4\%$ of the queued
          prefetches go to the L2 (``To lower level'' over ``Queued''). The rest hit in the L1D or
          merge with a request already in the queue (about 8\% of the queued prefetches). The
          prefetcher therefore re-requests the same lines many times: lookups with no benefit.
    \item \textbf{ChampSim's ``ISSUED'' counts every prefetch twice.} In this build, \texttt{pf\_issued}
          is incremented once when the prefetch enters the queue and again when its translation
          request is sent to the STLB, so $\texttt{ISSUED} = \texttt{PQ ACCESS} + \texttt{PQ TO\_CACHE}$
          exactly in all three traces (for Trace1, $155\,922 + 142\,926 = 298\,848$). We therefore
          report the number of queued prefetches instead of ``ISSUED''.
    \item \textbf{Page-boundary rule works.} There are zero cross-page prefetches in all traces,
          as the code intends.
    \item \textbf{Trace3 has the least to gain}: its baseline L1D load MPKI is already low ($3.40$),
          so even a perfect prefetcher could remove only a small number of misses.
\end{itemize}
These results are the reference point for the SPP evaluation. 
% ---------------------------------------------------------------- Task 1B
\subsection{Task 1B: Stride Pattern Prefetcher (SPP)}
\label{sec:task1b}

\subsubsection{Design}
The SPP prefetcher keeps the per-IP organisation of the IP-stride prefetcher, but every IP entry
holds two predictors instead of one: a cheap \emph{uniform} predictor for constant strides and a
small \emph{signature table} for strides that follow a repeating pattern. A confidence counter in each
predictor is raised on correct predictions and lowered on wrong ones, so a single irregular access
no longer destroys what was learned. On top of this, a small prefetch filter measures how many
prefetches are useful, and the prefetch degree is throttled from that measurement.

\paragraph{Overview.}
Figure~\ref{fig:spp-overview} shows the structures. Only demand loads (\texttt{type == LOAD}) are
used for training and prediction. Strides are always measured in cache lines.

\paragraph{IP tracker.}
Like IP-stride, the trackers are a plain array of 24 entries, indexed by an 8-bit IP tag and
replaced in LRU order. Besides the IP tag and the last accessed cache line, each tracker holds:
\begin{itemize}
    \item a \textbf{uniform predictor}: a stride \texttt{uni\_stride} and a 2-bit confidence
          \texttt{uni\_conf};
    \item a \textbf{stride history} \texttt{hist[3]} with the last three strides of this IP;
    \item a private \textbf{signature table} of 4 sets $\times$ 4 ways. Each entry holds a 6-bit tag,
          the stride that followed the signature (\texttt{next}, 7 bits signed) and a 2-bit
          confidence. A confidence of 0 marks an invalid entry.
\end{itemize}
The \emph{signature} of an IP is the hash of its three-stride history (FNV-style mix of the three
strides); two bits of it select the set and six bits form the tag. A signature therefore stands for
``the last three strides were $a,b,c$'' and the table learns which stride $d$ usually comes next.

\paragraph{Training.}
On every demand load of a known IP the stride $s = \text{line} - \texttt{last\_line}$ is computed.
A stride of 0 (same line) is ignored. A stride larger than $\pm 63$ lines is treated as a jump: the
uniform predictor and the history are cleared and no learning takes place. Otherwise both
predictors are trained:
\begin{itemize}
    \item \textbf{Uniform predictor.} If $s = \texttt{uni\_stride}$, \texttt{uni\_conf} is
          increased (saturating at 3). Otherwise it is decreased by 1 (the miss penalty), and only
          once it has reached 0 is \texttt{uni\_stride} replaced by $s$. A constant-stride stream
          therefore needs three accesses to reach the usable confidence of 2, but one stray
          stride only costs one confidence step instead of the whole entry.
    \item \textbf{Signature table.} The signature of the \emph{old} history is looked up. On a hit
          whose \texttt{next} equals $s$ the confidence is increased (saturating at 3), otherwise it
          is decreased and the entry is cleared when it reaches 0. On a miss the weakest way of the
          set is chosen: if its confidence is 0 it is replaced by a new entry with
          $(\text{tag}, s, 1)$, otherwise its confidence is only decreased. Stale or strong entries
          are thus replaced gradually and not at the first conflict.
\end{itemize}
Finally $s$ is shifted into \texttt{hist} and \texttt{last\_line} is updated.

\paragraph{Uniform / non-uniform classification and fallback.}
An IP is classified as \emph{uniform} when $\texttt{uni\_conf} \ge 2$, i.e.\ its recent strides have
mostly been the same. Otherwise it is \emph{non-uniform} and the signature table is used. This is
a fallback chain (Figure~\ref{fig:spp-flow}): constant strides are handled by the cheap
uniform predictor, which needs no history, and only IPs that are not uniform are handed to the
signature table, which can also follow alternating or otherwise periodic strides. If the
signature table has no confident entry for the current history, nothing is prefetched.

\paragraph{Prefetch generation, degree and page limit.}
In uniform mode up to \texttt{degree} lines $\text{line} + d\cdot\texttt{uni\_stride}$ are requested.
In pattern mode the predictor walks ahead: it looks up the signature of the current history, takes
the predicted \texttt{next} stride, adds it to the running line address, shifts it into a temporary
copy of the history and repeats, so the lookahead follows the learned pattern step by step and stops
as soon as there is no entry of confidence $\ge 1$. Every candidate must stay inside the
\textbf{same 4\,KB page} as the demand access, since the next physical page is unknown; the first
candidate that crosses the page ends the walk. The fill level depends on the miss-handling pressure:
a prefetch fills the L1D when fewer than half of the MSHRs are occupied, and otherwise only
the L2C, so prefetches do not starve demand misses.

\paragraph{Prefetch filter and usefulness tracking.}
Each issued prefetch is recorded in a 64-entry direct-mapped filter (valid bit and 12-bit tag).
It has two roles. First, a candidate already present in the filter is not requested again
(duplicate suppression). Second, when a later demand load hits a line recorded in the filter,
that prefetch is counted as \emph{useful} and the entry is cleared. This gives the prefetcher
its own accuracy, $\text{useful}/\text{issued}$, independent of ChampSim's counters.

\paragraph{Accuracy-based throttling.}
Issued and useful prefetches are counted over an epoch of 256 issued prefetches. At the end
of an epoch the accuracy is computed and the degree for the next epoch is chosen from three
levels: a low degree (1) if accuracy is below 40\,\%, a high degree (4) if it is above 75\,\%, and a middle degree (2)
otherwise; the counters are then reset. Thus the prefetcher is aggressive when its predictions
are good and falls back when they are mostly wrong, which limits cache pollution and wasted
bandwidth. The choice of the thresholds and degrees is discussed in
Section~\ref{sec:throttling}.

\paragraph{Example.}
Consider an IP with the stride sequence $+1,+3,+1,+3,\dots$, which IP-stride can never prefetch.
Its uniform predictor keeps being contradicted, so \texttt{uni\_conf} stays below 2 and the IP is
non-uniform. The signature table, however, learns the two entries
$(+1,+3,+1)\!\to\!+3$ and $(+3,+1,+3)\!\to\!+1$; after a few repetitions their confidence is
$\ge 1$ and, from the current history, SPP prefetches
$+3,+1,+3,\dots$ lines ahead, up to the degree. A single irregular stride in a constant stream
only lowers \texttt{uni\_conf} by one, so the stream remains classified as uniform and keeps being
prefetched.

\subsubsection{Accuracy-based throttling}
\label{sec:throttling}
\paragraph{Threshold selection.}
The throttle works on epochs of $N=256$ issued prefetches. At the end of an epoch the accuracy is
$\text{acc} = 100\cdot\text{useful}/\text{issued}$ (integer percent), computed from the prefetcher's own
filter counters (Section~\ref{sec:task1b}), and the degree for the next epoch is
\[
\text{degree} =
\begin{cases}
1 & \text{acc} < T_{\text{low}} = 40\,\%,\\
4 & \text{acc} > T_{\text{high}} = 75\,\%,\\
2 & \text{otherwise.}
\end{cases}
\]
The counters are reset after every epoch, so the decision always reflects only the most recent 256
prefetches. The epoch is counted in issued prefetches rather than in cycles or accesses, so the
accuracy estimate always has the same sample size, and 256 is large enough that one noisy
prefetch moves the estimate by less than 0.4 percentage points.

The two thresholds split the accuracy range into three regions with a different cost of a wrong
prefetch. Below 40\,\% most prefetches are wasted, and each
wrong prefetch occupies an MSHR and L2/L1 bandwidth and can evict a useful line, so the prefetcher
is throttled to the minimum. Above 75\,\% at least three of four prefetches are used, so going
deeper is worth it. In between the effect of the degree is unclear and a moderate value is kept.
The measured accuracy of IP-stride on our traces (53\,\%, 38\,\% and 16\,\%, Table~\ref{tab:task1a-main})
also lies around and below the lower threshold, which shows that a low-accuracy region needs to be
handled explicitly.

experimentally. All other SPP parameters were kept at their final values, and only the

instructions). Table~\ref{tab:spp-thr-sweep} compares the chosen setting with three other threshold

therefore act on the own-accuracy scale. With 40/75, 75\,\% on this scale separates the regular

\paragraph{Choice of prefetch degrees.}
The three levels are chosen to give the throttle a clear role for each accuracy region:
\begin{itemize}
    \item \textbf{Degree 1 (accuracy $<40\,\%$).} The lowest degree that still keeps the prefetcher
          running. It prefetches only the next predicted line, the one with the highest confidence,
          so the cost of wrong predictions is minimal, while the prefetcher can still recover when
          the program enters a regular phase. The prefetcher is not switched off completely, because
          then no new usefulness would be measured and the degree could never rise again.
    \item \textbf{Degree 2 (between 40\,\% and 75\,\%).} The default and the start value. It hides
          more latency than degree 1 while limiting the waste if some predictions are wrong.
    \item \textbf{Degree 4 (accuracy $>75\,\%$).} For regular streams, where the lines farther
          ahead are almost always used. A deeper lookahead is needed to be timely, since the
          prefetch has to complete before the demand access arrives. Four is the maximum, because
          it is kept within the page limit (a 4\,KB page has only 64 lines) and because a large
          degree raises the pressure on the MSHRs and the prefetch filter (64 entries).
\end{itemize}
The degrees are in a $1:2:4$ ratio so that each step is clearly different from the next.

\subsubsection{Discussion}
\paragraph{Where SPP wins against IP-stride, and why.}
\begin{itemize}
    \item \textbf{Irregular but repeating strides (Trace3).} IP-stride only prefetches when the
          same stride appears twice in a row. SPP's signature table also learns strides that follow
          a repeating pattern. On Trace3 39\% of SPP's prefetches come from the pattern path, and this
          is the trace where SPP gains most: coverage $2.5\% \to 4.3\%$, accuracy
          $16.0\% \to 26.1\%$ and speedup $1.0023 \to 1.0038$.
    \item \textbf{Tolerance to single wrong strides.} IP-stride replaces its stride after every
          mismatch, so one irregular access stops its prefetching until the stride repeats again.
          SPP's confidence counter only loses one step, so a stream with occasional noise keeps being
          prefetched.
    \item \textbf{Throttling and filtering.} The filter and the degree throttle cut the number of
          queued prefetches roughly in half without losing coverage. This saves L1D tag lookups,
          prefetch-queue slots and L2 bandwidth, which IP-stride (fixed degree 3) spends on lines
          that are already present.
\end{itemize}

\paragraph{Where SPP does not win, and why.}
\begin{itemize}
    \item \textbf{Constant-stride streams (Trace1).} For streams that IP-stride already handles,
          SPP can only match it. Both reach about $5.4\%$ coverage, and the speedup difference
          ($0.0003$) is within the noise of these runs.
    \item \textbf{Misses that are not stride-predictable (Trace2).} No variant we tried moved
          Trace2 above $0.7\%$ coverage. Its misses come from IPs whose consecutive addresses have no
          stable stride or short stride pattern, which a per-IP stride prefetcher cannot predict.
\end{itemize}

\paragraph{Why the speedups are small for both prefetchers.}
\begin{itemize}
    \item \textbf{The traces are front-end bound.} The baseline L1I MPKI is $14.5$, $40.0$ and
          $2.1$, and the branch MPKI is $16.1$, $6.3$ and $7.2$. Trace1 and Trace2 spend much of their
          time waiting for instructions or recovering from mispredictions, so removing a few
          percent of the data misses changes the IPC very little. Trace3 has few misses of any
          kind (L1D load MPKI $3.4$), so there is little left to remove.
    \item \textbf{Only a small part of the misses is stride-predictable.} An offline analysis of
          the load streams showed that only about 6--12\% of the loads can be predicted by a per-IP
          uniform or signature scheme even with unlimited tables, which bounds the coverage of both
          prefetchers.
    \item \textbf{A small tracker table.} Each trace has $73$k--$170$k distinct load IPs, and
          24 trackers hold the IP of only about one load in five. An earlier experiment with the
          initial SPP parameters showed that a larger table helps: 128 trackers gave speedups of
          1.004/1.002/1.005, and 512 trackers 1.006/1.007/1.015. But 512 trackers need about
          23\,KB, against 1.1\,KB for the final design. We kept 24 trackers to stay lightweight
          and to compare with IP-stride at the same number of entries.
\end{itemize}

The first version of SPP used a 5-stride history, a uniform threshold of 3 with miss penalty 2,
signature confidence $\ge 2$ and 12-bit IP tags. It was more conservative than IP-stride and had
\emph{lower} coverage. Table~\ref{tab:spp-tuning} shows how each change moved the results. The

\subsection{Task 2A: Instruction-conscious L2 replacement (I-RRIP)}
\label{sec:task2a}

\subsubsection{Design}

\paragraph{Passing the instruction bit.} \texttt{update\_replacement\_state} now takes an extra last
argument \texttt{uint8\_t isInstruction}. The declaration in \texttt{inc/cache.h}, every
\texttt{replacement/*} file and every call site in \texttt{src/cache.cc} and \texttt{src/ooo\_cpu.cc}
were updated. Call sites pass the \texttt{instruction} field of the packet being filled or hit. \newline
The policy treats a request as an instruction request only if
\texttt{isInstruction \&\& (type == LOAD || type == PREFETCH)}. This is the same rule
\texttt{fill\_cache} uses to set \texttt{block.instruction} in the L2C. \newline
\texttt{find\_victim} does not receive the flag, so
it reads \texttt{current\_set[way].instruction}.

\paragraph{Policy} (\texttt{replacement/irrip.l2c\_repl}). I-RRIP is SRRIP with a 2-bit RRPV
(0 = near, 3 = distant) that treats instruction lines, data lines and writebacks differently.

\begin{table}[H]
    \centering
    \begin{tabular}{lcc}
        \toprule
        Event & SRRIP (given \texttt{rrip.l2c\_repl}) & I-RRIP \\
        \midrule
        Fill, instruction line   & 2 & 2 \\
        Fill, data line          & 2 & 3 \\
        Fill, writeback          & 2 & 3 \\
        Hit, instruction line    & 0 & 0 \\
        Hit, data line           & 0 & 2 \\
        Hit, writeback           & 0 & unchanged \\
        Victim                   & first line at 3 & first \emph{data} line at 3, else first line at 3 \\
        \bottomrule
    \end{tabular}
    \caption{RRPV assigned on each event. If no line is at 3, all RRPVs in the set are incremented and the search repeats.}
\end{table}

\paragraph{Storage.} 2 bits $\times$ 1024 sets $\times$ 8 ways $= 2$~KB, the same as SRRIP. The
instruction bit is already stored with each L2C block, so no new state is needed.

\paragraph{How the values were chosen.} The six values above and the eviction preference were parameters that we changed from
run to run to observe how the speedup and MPKI change. We ran simulations on combinations with the same philosophy: that we should
prioritize instruction lines staying in the cache over data lines. This means that we always inserted instruction lines with an RRPV value
that was $\leq$ the insertion RRPV of data. We then checked the average L2 instruction MPKI and speedup and chose the best one accordingly.


\subsubsection{Rationale}

The table below starts from the final policy and changes one decision at a time (geomean speedup
over LRU; MPKIs are averages over the three traces). The last rows are the starting point we
tried first and RRIP-like settings.

\paragraph{Reading the RRPV.} The RRPV of a line is a prediction of how soon it will be reused: 0
is kept longest, 3 is the next victim. A fill enters at an intermediate value and has to be hit
to be promoted. When no line in the set is at 3, every RRPV in the set is incremented by one (an
\emph{aging step}) and the search repeats. This happens only on a miss. So the RRPV a class of
lines gets on fill and on hit decides how many aging steps (misses to that set) it survives.
Table~\ref{tab:task2a-protect} lists this for I-RRIP.

\begin{table}[H]
    \centering
    \begin{tabular}{lcc}
        \toprule
        Line class & RRPV & Aging steps before it can be evicted \\
        \midrule
        Writeback fill, or data fill that is never hit & 3 & 0 \\
        Instruction fill, never hit                    & 2 & 1 \\
        Data line after a hit                          & 2 & 1 \\
        Instruction line after a hit                   & 0 & 3 \\
        \bottomrule
    \end{tabular}
    \caption{Protection given to each class of line in I-RRIP. Within the same RRPV, data lines are evicted before instruction lines. A data line never ranks above an instruction line.}
    \label{tab:task2a-protect}
\end{table}

\paragraph{Insertion (modified, the largest effect).} SRRIP inserts every line at 2. The idea
behind inserting below the maximum protection is scan resistance: a line that was just fetched has
shown no reuse yet, so it should not displace lines that have. Two properties of the L2 make
the type of a line a useful extra signal, and I-RRIP uses them to choose a different insertion
value for each type.
\begin{itemize}
    \item \textbf{Instruction lines reuse more, and their misses cost more.} The code footprint
          is larger than the L1I, so code that the L1I evicts is fetched again, and the L2 is where
          it is found. Code is also executed repeatedly (loops, shared library functions). An
          instruction miss stalls fetch and decode, so the core has nothing to execute, while an
          out-of-order core can overlap part of a data miss with other work. Both facts argue for
          keeping instruction lines longer.
    \item \textbf{Data lines at the L2 are often not reused.} The L1D has already absorbed
          the short-range temporal reuse, so a data line filled into the L2 is often touched once
          (streaming or scan-like accesses). Keeping such a line costs a way that an instruction line could use.
    \item \textbf{Writebacks are not demand requests.} A written-back line only moves the L1D's
          dirty copy down; nothing shows that the program will read it from the L2 again soon.
\end{itemize}
This gives the insertion values: \emph{data and writebacks at 3} (next victim, they leave first
unless a hit proves reuse) and \emph{instruction lines at 2} (one aging step of grace). The data
value is the most important decision in the policy. Placing data at 2 instead keeps one-shot
data around for an extra aging step, so it competes with instructions and the speedup falls from 1.0216 to 1.0114
and the average instruction MPKI rises from 5.94 to 7.32 (Table~\ref{tab:task2a-ablation}). The cost
of data at 3 is that some data lines which would have been reused after a longer gap are lost,
so the data MPKI rises. That is the intended trade, because the instruction misses saved are more costly. Writebacks
behave the same way: at 2 instead of 3 they push the instruction MPKI up (5.94 to 6.37) and the
speedup down (1.0157).

Instruction lines are deliberately \emph{not} inserted at 0, even though 0 looks like stronger
priority. The RRPV only carries information if a fresh line and a line that has been hit
have different values. At 0 they look the same, and equal RRPVs are resolved by way index (the
victim search takes the first match), not by recency. A code line that is never fetched again then
stays as long as hot code. Inserting at 0 gives a speedup of 1.0118 and at 1 of 1.0148, against 1.0216
at 2, and Trace1 falls below LRU (0.994 at 0). On Trace2 the instruction MPKI is higher at 0 than at 2 (9.80 against 8.22), so the extra priority
does not even reduce instruction misses. At 2 a line has to be hit to reach 0, so the RRPV separates proven
code from unproven code.

\paragraph{Promotion (modified).} A hit is the only evidence of reuse that the policy gets, and
SRRIP uses it by resetting the RRPV to 0 (hit priority). I-RRIP keeps that for instruction lines
and weakens it for data. The strength of the promotion follows how reliable the evidence is and what a miss on
the line would cost.
\begin{itemize}
    \item \textbf{Instruction hit $\to$ 0.} A code line that is hit again is likely to be hit again,
          and its miss is expensive, so it gets the full promotion to RRPV=0.
          Promoting to 1 instead removes one step; the speedup falls to 1.0174 and the instruction MPKI rises
          to 6.16.
    \item \textbf{Data hit $\to$ 2.} A single hit on a data line is weaker evidence than a hit on code,
          and the line is cheaper to lose, so we tried all four values.
          Promoting to 0 or 1 protects a once-hit data line for three or two aging steps. That is as long
          as, or longer than, a fresh instruction line, so data crowds out code (instruction MPKI 6.51 and 6.23,
          speedup 1.0191 and 1.0203). At 2 a hit keeps the line for one aging step, like a fresh instruction line,
          and data-first eviction settles ties. The instruction MPKI falls to 5.94 and the speedup is the
          best, 1.0216. At 3 a hit gives no protection. The instruction MPKI stays at 5.94, but the data MPKI
          jumps to 8.55 and the total L2C load MPKI to 14.48 (13.96 at 2), and the speedup drops to 1.0203.
          So 2 is the point where a hit still counts but a data line never ranks above an instruction line.
    \item \textbf{Writeback hit $\to$ unchanged.} A writeback that finds its line in the L2 is the L1D
          returning a dirty copy. The program has not read the line from the L2, so promoting it would
          measure L1D traffic and not L2 reuse. The given SRRIP promotes it to 0, which keeps lines
          that are not being reused. Leaving the RRPV alone is the only difference between SRRIP and the policy
          with all fills at 2, and it is worth +0.4\% by itself (1.0045 against 1.0008).
\end{itemize}

\paragraph{Eviction (modified, small effect).} SRRIP evicts the first way at the maximum RRPV, and ages the set when none
is there. I-RRIP keeps this order and adds a tie-break: among the ways at RRPV 3, a data line
is evicted before an instruction line. The RRPV is the reuse prediction, and when two lines have the same
prediction the cheaper miss should go first. The type is therefore a second criterion and not a
hard partition. We do not evict data lines first regardless of RRPV, because a stale instruction
line (one that was hit long ago and has aged to 3) must be able to leave. Instruction lines are
not pinned: the aging step always brings them to 3, and when no data line is at 3 an instruction line is
evicted. Invalid ways start at 3 and are not instruction lines, so they are used first.

The tie-break matters because data and instruction lines often share an RRPV: a once-hit data line and a fresh
instruction line are both at 2, and a stale instruction line and a one-shot data line are both at 3. Data-first
eviction makes the data line leave first in both cases. Without it the speedup is 1.0214 against 1.0216 and the
instruction MPKI is 6.13 against 5.94 (Trace2: 8.68 against 8.22). The effect is small and not uniform:
Trace1 is marginally better without it (1.0062 against 1.0055, with a lower data MPKI of 9.51 against 9.71),
but Trace2, Trace3 and the average favour it.

\paragraph{Why this design.} The three changes work together. Insertion and promotion set the
ranking, and the eviction preference only breaks ties at RRPV 3. Moving from RRIP to the final policy
is worth +2.1\% of speedup and a 42\% drop in average L2 instruction MPKI (10.19 $\to$ 5.94).
Settings that give lower data MPKI (e.g.\ data inserted at 2) lose speedup and raise
instruction MPKI. The final policy also has essentially the lowest average L2 instruction MPKI of all 112
policies we simulated (a variant that does not promote data hits is lower by 0.001, 5.936, but has a lower speedup),
so both goals (speedup and L2 instruction MPKI) are met by the same policy.

\paragraph{Wider RRPV (not adopted).} We also tried a maximum RRPV of 4, 5 and 7 with the same structure
(instruction at max$-1$, data and writebacks at max). The best 3-bit policy reached 1.0256 (+0.4\% over the final 2-bit policy) but needs 3~KB, so we keep the 2-bit design. Run logs (ChampSim output) are in \texttt{results/task2/maxrrpv}.

\subsection{Task 2B: Dynamic I-RRIP}
\label{sec:task2b}

\subsubsection{Design}

I-RRIP lowers instruction misses at the price of more data misses (data MPKI rises by 12--32\% over LRU).
That trade is only worth it when instruction misses are the costlier ones. A workload with a small code footprint
or with critical data reuse can do better with plain RRIP. Dynamic I-RRIP therefore chooses between the two
policies at run time with \emph{set dueling}.

\paragraph{Leader and follower sets.} Of the 1024 L2C sets, 32 are \emph{RRIP leaders} (set index $\bmod 32 = 0$)
and always run SRRIP. Another 32 are \emph{I-RRIP leaders} ($\bmod 32 = 16$) and always run I-RRIP. The remaining
960 are \emph{followers} and copy whichever policy is currently winning. The leaders are interleaved
through the cache, so both groups sample the same program phases and address range as the followers.

\paragraph{Decision rule (final: PSEL duel).} A 10-bit saturating counter, PSEL, starts at 512.
A demand miss (load, RFO or prefetch) in an RRIP leader \emph{increments} PSEL and a miss in an I-RRIP
leader \emph{decrements} it, so PSEL rises when RRIP is missing more. Followers use I-RRIP when
$\text{PSEL} \ge 512$ and SRRIP otherwise. An instruction miss moves PSEL by $W=4$ and a data miss
by 1. In SRRIP mode a set behaves exactly like the given \texttt{rrip.l2c\_repl} (fill at 2, hit to 0).
In I-RRIP mode it uses the Task~2A policy.

\paragraph{Threshold rule} We also implemented the rule suggested in the problem statement.
The RRIP leaders count instruction accesses and misses against all accesses and misses, and followers use
I-RRIP when
\[
  \frac{\text{instr\_acc} + \text{instr\_miss}}{\text{tot\_acc} + \text{tot\_miss}} > T .
\]
The ratio is evaluated once every 1024 RRIP-leader events, not on every access, and then all four counters are halved.
A ratio taken from only a few events is noisy, and every change of decision switches the follower sets between two different
insertion and promotion behaviours, so deciding on noise would make them alternate. 1024 events average out short bursts, and the
division and comparison are done once per 1024 accesses instead of per access, with one decision bit kept in between. The run is still
short enough to follow phases: the leaders see about 3\% of the L2C traffic, so 1024 events give roughly 60 decisions per run.
The halving of the counters is explained in the rationale below. Both rules
are in \texttt{replacement/dyn\_irrip.l2c\_repl}. The macro \texttt{USE\_PSEL} selects one of them
(1 = PSEL duel, the final design; 0 = threshold). The ratio counters keep running in the PSEL design, only to report
the instruction share in the statistics.

\paragraph{Storage.} The PSEL design needs one 10-bit counter. The leader tests only compare the low five bits of the
set index. The threshold rule would add four 11-bit counters, a 10-bit event counter and one decision bit (about 55 bits).

\subsubsection{Rationale for the leader sets and decision logic}

\paragraph{Why set dueling.} The better policy depends on the program and on its phase, and we cannot know it in
advance. Dueling measures it directly: the leader sets run both policies side by side on the \emph{same} access stream,
so their miss counts are a fair, up-to-date comparison, and followers follow the best one after both are tested.

\paragraph{Number and layout of leader sets.} 32 leader sets per policy (3\% of the cache each) are enough to collect
thousands of misses per run, so PSEL is stable, while keeping 94\% of the cache under the winning policy. Fewer leaders
make the estimate noisy. More leaders force more sets to run the losing policy. The layout is static and interleaved
(offsets 0 and 16 of a 32-set stride). The 32-leader, 10-bit configuration follows the
sizes commonly used for set dueling (DIP/DRRIP).
These sizes were kept fixed; only the decision parameters below were changed for different runs.

\paragraph{Why instruction misses are weighted.} PSEL counts misses, which assumes every miss costs the same. That is not true
here, and it is the very reason I-RRIP exists. An instruction miss stops the front end: nothing new can be fetched or
issued until the line returns, so the whole pipeline starves. A data miss only delays the instructions that depend on it, and
out-of-order execution can keep working on independent instructions in the meantime. I-RRIP therefore deliberately trades
cheap data misses for expensive instruction misses, and it can even \emph{increase} the total number of misses while
improving IPC. This happens on Trace1. A duel that counts every miss equally ($W=1$) would judge I-RRIP only by its total miss count and
reject it there. Counting an instruction miss as $W>1$ data misses makes PSEL measure approximate stall cost
instead of raw misses. $W$ must at least equal the ratio of data misses gained to instruction misses saved
(about 1.6 on Trace1).

\paragraph{Why the ratio is not a good rule on its own.} The threshold rule tests how many instruction accesses there are
and \emph{assumes} that I-RRIP helps when there are many. It never observes whether I-RRIP actually reduces the misses.
PSEL measures the outcome, which is the reason it is our final choice. The sensitivity study below confirms it.

\paragraph{Why the ratio is evaluated once per 1024 events, and why the counters are halved.}
A decision from a few events is noisy, and flipping the follower policy on noisy data makes the sets alternate between two
insertion/promotion behaviours. Averaging over 1024 events smooths bursts. The evaluation is also cheap in hardware:
one division and one comparison per epoch instead of per access, with a single decision bit kept in between.
The size of a run cannot be much longer either: the leaders see about 3\% of the L2C traffic, so 1024 events give roughly 60 decisions
per run, whereas a much longer epoch would give only one or two.
At the end of each epoch the counters are \emph{halved} (a one-bit right shift). Without this the counters would only
grow and the ratio would become a whole-run average that cannot follow a phase change. Resetting them to zero instead
would base every decision on only the last 1024 events.

\subsubsection{Sensitivity study}

We swept the decision parameter of each rule: five thresholds $T \in \{0.20, 0.25, 0.30, 0.55, 0.70\}$ for the
threshold rule (A) and five weights $W \in \{1, 2, 3, 4, 6\}$ for the PSEL rule (B), on all three traces.
The measured instruction share in the RRIP leaders (averaged over epochs) is 0.44 (Trace1), 0.56 (Trace2) and 0.41 (Trace3).
It varies a lot within a run (per-epoch minimum--maximum: 0.21--0.52, 0.02--0.68 and 0.08--0.54).

    \item \textbf{$W=1$ fails on Trace1 only.} The duel sees I-RRIP missing more in total, picks RRIP (2\% I-RRIP fills) and Trace1

\paragraph{Weighting data misses as well.} We also gave data misses a weight $d>1$ ($d\in\{2,3\}$). Only the ratio $W/d$ matters for which
policy wins, so this is equivalent to lowering $W$, with a faster-moving PSEL. As expected, it never helped: no combination beat $d=1$.
A larger $d$ makes data misses count more, which pushes the duel towards RRIP and away from the policy that trades data misses for
instruction misses. Trace1, where this trade is the tightest, suffers most and Trace2 loses part of its gain at the largest $d$,
while Trace3 is unaffected. Ratios just above the break-even were also poor on Trace1: the two policies then look almost equally good, so the duel
is decided by a thin margin and the followers probably alternate between them, which gives up the benefit of both. The instruction weight
needs a clear margin over the data weight, so we keep $d=1$ and only tune $W$.

instead of one that collapses from 1.0185 to 1.0009, and no per-workload tuning. The threshold rule needs a value of $T$ below
the lowest ratio of every workload to stay safe, in which case it adds nothing over always using I-RRIP.

\paragraph{Observations.}
\begin{itemize}
    \item \textbf{Dynamic I-RRIP finds the better policy on its own.} Its speedup (1.021) is essentially that of static I-RRIP and
          about two points above RRIP, and it removes about 40\% of RRIP's L2 instruction misses. PSEL stays far above its midpoint on all
          three traces, so the duel picks I-RRIP consistently, in the same proportion as in the sweep.
    \item \textbf{It cannot beat static I-RRIP on these traces.} I-RRIP is already better than RRIP on all three, so the best the duel can do is
          choose I-RRIP everywhere. Set dueling has a built-in cost: the RRIP leader sets always run the losing policy, and a few follower fills
          still use RRIP while PSEL moves. This cost scales with the gain: it is visible on Trace2, where I-RRIP helps most, and negligible on Trace3,
          where it helps little.
    \item \textbf{Trace1 shows why the weight matters.} Here the duel is closest to a tie, because I-RRIP saves instruction misses but adds data misses.
          The weighted PSEL still resolves it in favour of I-RRIP, and the few sets that stay in RRIP mode even keep data misses slightly lower. We
          treat the small gain over static I-RRIP as incidental rather than a general benefit.
    \item \textbf{The value of the dynamic policy is robustness, not peak speedup.} A fixed policy, or a threshold set for one workload, loses
          whenever the workload changes: the sweep shows threshold rules falling back to RRIP's level. The duel needs no workload knowledge. On a program where
          I-RRIP hurt, PSEL would drop below its midpoint and the followers would switch to SRRIP.
\end{itemize}

\section{Task 3: Incorporating SPP with Dynamic I-RRIP}
\label{sec:task3}

\subsection{Design}

The L1D now runs the Stride Pattern Prefetcher of Task~1B. A prefetch that misses in the L1D travels to the L2C as a packet of
type \texttt{PREFETCH}, and it fetches data only (instruction prefetching is off). The replacement policy tells these packets apart from
demand requests by the packet type and, on a hit, by the per-line ``brought by a prefetch'' bit that ChampSim already keeps
for its prefetch statistics. The three prefetch rules below live in \texttt{replacement/dyn\_irrip.l2c\_repl}. They are active in
I-RRIP mode only, so the SRRIP leader sets, and the followers while they run SRRIP, remain the plain SRRIP baseline of the duel.
Instruction lines are handled exactly as in Task~2B.

\begin{table}[H]
    \centering
    \resizebox{\textwidth}{!}{%
    \begin{tabular}{lll}
        \toprule
        Event (data prefetch) & Task 2B behaviour & Prefetch-aware behaviour \\
        \midrule
        Fill by a prefetch              & RRPV 3 (as any data fill)  & RRPV 3 (\texttt{PF\_INS}) \\
        Prefetch hits a resident line   & promote to 2               & leave the RRPV unchanged \\
        First demand hit on a prefetched line & promote to 2         & RRPV 2 (\texttt{PF\_HIT\_PROMO}) \\
        \bottomrule
    \end{tabular}}
    \caption{Handling of prefetch packets in I-RRIP mode.}
\end{table}

The set-dueling logic is untouched: prefetch accesses still count in the leader sets. The only added state is the one-bit
``prefetched'' flag per line (1~KB for the 8192 lines of the L2C).

\subsection{Rationale for handling prefetch packets}

\paragraph{A prefetched line is speculative.} A replacement policy ranks lines by expected reuse. A demand-fetched line has proven
that the program wants it. A prefetched line only has a guess behind it, and SPP's guesses are right 43\% of the time on
average (accuracy 26--57\% across the traces). Giving such a line the same standing as a demanded one lets wrong guesses
displace lines with proven reuse. That hurts most for instruction lines, which I-RRIP exists to protect. We therefore insert prefetch
fills as distant (RRPV 3), where they are the first candidates for eviction if they are not used.

\paragraph{A prefetch hit is not evidence of reuse.} If a prefetch finds the line already in the L2C, SPP merely asked for it again.
No instruction has used it, so promoting it would hand the protection reserved for reused lines to a speculative request. We leave the
RRPV unchanged.

\paragraph{A prefetched line is mostly dead in the L2C after its first use.} SPP chooses the fill level of each prefetch from the
L1D's MSHR occupancy: below half full the line is brought into the L1D (and passes through the L2C), otherwise it is placed in the L2C only.
In the first case the L1D serves the demand access, and the L2C copy is a second copy that is needed only if the L1D evicts the line early.
In the second case the demand access hits the L2C, and this hit is the one useful event that the line will ever have there.
Either way the line is not part of a reuse pattern that the L2C should keep: once its demand access has been served, nothing in the stream
suggests that it will be needed again. The first demand hit on a prefetched line therefore does not earn the full promotion to RRPV 0,
and the line is not kept near. We set it to 2, the same value as an ordinary data hit, so it still gets one aging step of protection.

\paragraph{What we tested.} We swept the insertion value and the value after the first demand hit, with two further options
(excluding prefetches from the duel, and demoting a line on a prefetch hit). The measurements agree with the reasoning, but the
differences are small:
\begin{itemize}
    \item \textbf{Insertion at 2 is worse than at 3} in every combination (geomean speedup 1.0220--1.0226 against 1.0240--1.0244), so
          keeping prefetches distant is right: protecting speculative lines costs more in pollution than it gains.
    \item \textbf{Promoting a line to 0 on its first demand hit is worse} than to 2 or 3 (1.0240 against 1.0244), which supports the
          ``dead after first use'' argument.
    \item \textbf{Excluding prefetches from the duel, and demoting on a prefetch hit, change nothing measurable} (within 0.0002),
          so they are not used. Prefetch traffic in the leader sets is too small to move PSEL.
\end{itemize}

\subsection{Discussion}

\begin{itemize}
    \item \textbf{It beats both baselines on every trace.} Against standalone SPP (SPP + LRU) the IPC gain is
          +0.7\%, +5.1\% and +0.7\% on Trace1, Trace2 and Trace3 (geomean speedup 1.0244 against 1.0027). Against Dynamic I-RRIP without a prefetcher it is
          +0.5\%, +0.1\% and +0.4\% (1.0244 against 1.0210).
    \item \textbf{Most of the gain over standalone SPP comes from the replacement policy.} SPP alone barely helps: its coverage is 3.4\% on average,
          and only 0.6\% on Trace2. The dynamic I-RRIP policy removes about 42\% of the L2 instruction misses relative to SPP + LRU
          and lowers the total L2C load MPKI by 17\%, at the price of more data misses, as in Task~2.
    \item \textbf{SPP adds a modest benefit on top of Dynamic I-RRIP, mostly on the traces where it covers misses.} The gain is
          0.4--0.5\% on Trace1 and Trace3, where coverage is 4--5\%, and only 0.1\% on Trace2, whose coverage is close to zero.
          Trace2 is dominated by instruction misses, which the L1D data prefetcher cannot help.
    \item \textbf{Prefetch awareness contributes a very small amount.} Compared with running the Task~2B policy unchanged under SPP, the prefetch-aware
          version moves the geomean speedup from 1.0243 to 1.0244. This is expected. SPP's prefetches are a small fraction of the L2C traffic, so there
          are few packets for the policy to treat differently, and the prefetch rules mostly agree with what the data rules of Task~2B already do
          (data is inserted distant, and a data hit is promoted to 2). Where they differ is only the ``prefetch hit is not reuse'' rule.
    \item \textbf{Accuracy and coverage are determined by SPP, not by the L2C policy.} They are almost the same in all SPP configurations
          (accuracy 43.2--43.5\%, coverage 3.4--3.5\%), and so is the L1D load MPKI (8.9). The L2C policy decides what stays in the L2C
          after SPP has made its decisions, so its effect shows up in the L2C MPKI and in IPC and not in the prefetcher metrics.
    \item \textbf{Accuracy varies a lot with the trace} (57\%, 47\% and 26\%). On Trace3 about three quarters of the prefetches are wasted, which is the
          case where distant insertion matters most: speculative lines do not displace the protected instruction lines.
\end{itemize}
